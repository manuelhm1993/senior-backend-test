## 1. Context and Objective

This exercise asks you to build a small distributed system made of two independent applications that must coordinate with each other over asynchronous messaging:

- **Client** — a standalone application that simulates a local/edge installation called the **Input Manager**.
- **Server** — a standalone application that simulates its cloud-side counterpart.

The two applications do not know about each other's internals. They only communicate through RabbitMQ. You are building this system from scratch, as a self-contained demonstration — it is not a feature meant to be merged into an existing production codebase, and it does not need to integrate with any external system beyond what is described here.

We are not primarily evaluating how much code you can produce. We are evaluating:

- how you read and disambiguate a requirements document that is intentionally incomplete in places;
- how you design two independently deployable applications and the contract between them;
- your Laravel and general backend engineering practice;
- your understanding of asynchronous messaging with RabbitMQ, including correct terminology;
- how you reason about the security of a pairing process;
- how you handle idempotency, retries, and failure;
- how you design a bidirectional synchronization flow;
- your use of Docker to make the environment reproducible for someone else;
- your testing discipline;
- your use of GitHub Actions for continuous integration;
- how you organize and communicate your work through issues, branches, and pull requests;
- how understandable your work would be to another developer who has to pick it up tomorrow;
- how you use AI tools responsibly and transparently.

No graphical interface is required. Every interaction may be implemented as a minimal web page or a CLI command. Visual polish is not part of the evaluation.

## 3. Functional Requirements — Client and Server

### 3.1 Client Application ("Input Manager")

1. On first startup, the Client must generate and persist a unique installation identifier (a ULID, or an equivalent mechanism of your choice).
2. The Client must expose, via a minimal web page or CLI, the information needed to pair the installation with the Server. Your design must clearly distinguish between:
   - a **public installation identifier**, and
   - a **pairing credential or secret token**, if you judge one to be necessary.

   We are deliberately not telling you which of these to use. Document and justify your decision. Do not assume that a ULID is, by itself, a secure credential — that assumption is exactly one of the things this exercise is designed to surface.

3. Before activation, the Client must remain in a waiting state, listening for a RabbitMQ message addressed specifically to that installation.
4. The activation message sent by the Server must contain, at minimum:
   - `workspace`
   - `facility`
   - basic information identifying the owner/responsible party
   - an initial list of instruments or devices
   - a message/contract version identifier
5. Processing the activation message must be safe against duplicate deliveries and against the Client process restarting mid-flow.
6. After activation, the Client must be able to publish a settings change over RabbitMQ, addressed to the Server.
7. The Client must be able to receive and apply a settings change published by the Server.

### 3.2 Server Application

1. The Server must allow, via a minimal web page or CLI:
   - selecting or creating a workspace;
   - selecting or creating a facility;
   - entering the pairing information generated by the Client;
   - associating that installation with the selected facility.
2. Completing the association must trigger an asynchronous job. That job must publish the activation message over RabbitMQ to the corresponding Client **only**.
3. The Server must be able to receive and apply settings changes published by the Client.
4. The Server must be able to publish settings changes addressed to the associated Client.
5. The Server must prevent inconsistent or duplicate associations and must maintain an understandable state for the activation process (e.g., it should be possible to tell, at any point, whether an installation is unpaired, pending activation, or active).

## 4. RabbitMQ Requirements

RabbitMQ is mandatory as the messaging backbone between the two applications.

You are expected to design and document your own exchanges, queues, routing keys/bindings, acknowledgement strategy, and basic error handling. Use correct RabbitMQ terminology throughout your documentation — in particular, do not use "channel" as a loose synonym for "queue" or "routing key"; a channel is a specific, distinct concept in the AMQP model.

This brief intentionally does not prescribe your topology. We define the outcomes we need to be able to observe and verify; you propose, implement, and justify the design that produces them.

At minimum, your implementation must demonstrably satisfy:

- The activation message reaches the correct Client — and only that Client.
- Acknowledgement behavior is consistent: messages are not silently lost, and successful processing is only acknowledged after it is safe to do so.
- Duplicate message delivery is handled safely (no duplicate side effects on the receiving end).
- Basic handling of messages that cannot be processed (malformed payload, unknown version, etc.) — the consumer must not crash, and the queue must not become permanently blocked because of one bad message.
- Every message carries a **message ID** and a **correlation ID**.
- Every message carries an explicit **contract version** field.
- When settings changes are relayed between Client and Server, this must not create an infinite loop of messages echoing back and forth.

## 5. Technical and Docker Constraints

- Both applications must be built in **Laravel**. The specific PHP and Laravel versions are your choice — state them in the README.
- Both applications, together with RabbitMQ, must be runnable **locally with Docker**.
- **Delivery structure:** we recommend a single repository containing two clearly separated codebases (for example, `client/` and `server/`), since this is the simplest structure to review fairly and keeps the two applications' independence visible. You may use two separate repositories instead if you have a concrete reason to — if so, explain it in the README. Whichever structure you choose, the logical and runtime independence between the two applications must remain clear: neither application should require internal knowledge of the other's codebase to function.
- The local environment must:
  - start with one command, or a small number of documented commands;
  - use persistent storage where it is actually needed (e.g., the Client's installation identity, the Server's workspace/facility/association state);
  - have no dependency on any cloud service;
  - require no real credentials of any kind;
  - include minimal seed data or fixtures needed to exercise the flow;
  - allow a reviewer to reproduce the complete pairing → activation → bidirectional synchronization flow end to end, from a clean checkout.

## 8. Observable Acceptance Criteria

These are the outcomes we will check for. They describe *what* must be true, not *how* to build it:

- The environment starts using only the documented command(s), with no undocumented manual steps.
- On first run, the Client generates an installation identifier that persists across restarts.
- Pairing information generated by the Client can be entered into the Server and associated with a facility.
- Completing that association results in the activation message being delivered to the correct Client, and no other.
- The Client applies the activation payload and leaves its waiting state.
- Resending the same activation message does not corrupt state or produce duplicate side effects.
- At least one settings change flows successfully from Client to Server.
- At least one settings change flows successfully from Server to Client.
- Automated tests exist, and they pass both locally and in the GitHub Actions run.
- The security reasoning behind the public-identifier-vs-secret-credential decision is explicitly written down, not just implied by the code.

## 11. Core Requirements vs. Optional Extensions

We would rather receive a small, correct, well-explained system than a large, unfinished, undocumented one. If the full scope above does not fit comfortably in the time box, use the following boundary.

**Core Requirements (must be present in any acceptable submission):**

- Two independent, Dockerized Laravel applications: Client and Server.
- A complete pairing and activation flow: installation identifier generated by the Client → pairing information entered on the Server → association triggers an async job → activation message delivered over RabbitMQ → Client applies it and leaves its waiting state.
- At least one settings synchronization from Client to Server.
- At least one settings synchronization from Server to Client.
- Basic idempotency: replaying the same activation message does not corrupt state or duplicate side effects.
- A README covering setup, architecture, the RabbitMQ flow, the public-identifier-vs-secret decision, and AI usage disclosure.
- At least one automated test.
- At least one GitHub issue showing task breakdown, and at least one pull request with a reviewer-oriented description.
- A minimal GitHub Actions workflow that runs the test suite.

**Optional Extensions (valuable, but not required for an acceptable submission):**

- Retry-with-backoff or a dead-letter mechanism for unprocessable messages.
- An explicit, tested anti-loop mechanism for the bidirectional settings echo.
- Broader automated test coverage (failure injection, concurrent activation attempts, etc.).
- Static analysis in CI (e.g., PHPStan/Larastan) or linting.
- Structured logging with correlation ID propagation across both applications.
- Basic rate limiting or abuse protection on the pairing endpoint.
- Support for more than one Client instance running concurrently in the demo environment.
- A demonstrated second version of the message contract, to show your versioning approach in practice.
- A more polished web UI beyond the minimal CLI/forms baseline.

An incomplete submission that clearly delivers the Core Requirements and honestly documents what was cut is a normal, acceptable outcome of a four-hour exercise.
